# 公開 DQMC ソフトウェアの命名メモ

## リポジトリの前提

- `AF_QMC` は完全な開発履歴、内部文書、raw データ、参考資料を保持する
  private repository とし、今後も公開しない。
- 公開時は、コードと公開可能な一部文書を `AF_QMC` から抽出し、
  別の public repository を作成する。

## 命名で重視する条件

- DQMC ソフトウェアとして検索しやすく、既存ソフトウェアと区別できる。
- 日本語話者・英語話者の双方が発音しやすい。
- 現在の半充填 Hubbard 模型向け実装を不必要に誇張しない一方、
  将来の機能拡張を妨げない。
- AI は開発プロセスの特徴であり実行時アルゴリズムではないため、
  AI を用いた新しい QMC 手法だと誤解させない。
- 「形式検証済み」「完全に汎用」など、実際より強い保証を連想させない。
- ソフトウェア名、public repository 名、実行ファイル名を無理なく揃えられる。

## 検討した名称

### VeriDQMC

- validation を重視した本コードの開発方針とは対応する。
- DQMC コードであることが名称から分かり、簡易的な GitHub / Web 検索では
  完全一致する既存プロジェクトは見つからなかった。
- 一方で、名称として直感的に響かず、`Veri` が形式検証や強い保証も
  連想させ得る。
- **結論: 現時点では採用しない。**

### KasaneQMC

- 虚時間スライス、行列積、UDV stack を「重ねる」という実装上の特徴と
  対応し、日本語由来の固有性がある。
- 一方で、名称だけでは DQMC コードの特徴が直ちには伝わりにくく、
  `Kasane` 単体は他分野のソフトウェアでも使われている。
- **結論: 候補として保留するが、現時点では決定しない。**

### 現時点で避ける名称

- `AIDQMC` / `AgentDQMC`: AI がQMCアルゴリズム自体に組み込まれているとの
  誤解を招きやすい。
- `AFQMC`: auxiliary-field QMC の一般名との区別が難しく、private repository
  `AF_QMC` とも混同する。
- `DQMC-C` / `OpenDQMC`: 一般的すぎて、検索性と固有性が弱い。

## 今後の進め方

- 急いで決定せず、説明的な名称と固有ブランド名のどちらを重視するかを
  含めて再検討する。
- public repository を作成する前に、候補ごとに GitHub、Web、論文検索、
  関連分野のパッケージ名を再確認する。
- 正式名称を決めた後に、repository 名、README の一文説明、
  executable 名、論文中の表記をまとめて確定する。
