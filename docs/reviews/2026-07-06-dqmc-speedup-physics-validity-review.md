# DQMC 高速化まとめ — 物理的妥当性レビュー

対象: `docs/2026-07-04-dqmc-speedup-summary.html` と現行 `src/` 実装。

## 1. 各最適化の妥当性判定

### (1) UDV 部分積スタック安定化 — 妥当(厳密な再編成)

- suffix スタック `S[j] = B_{L-1}…B_{b_j}` (`green_stack_build_suffix`) と
  prefix `B(τ,0)` の結合 `combined = prefix·suffix` (`udv_combine` は
  `L·R` の順で結合) は Green 関数の定義
  `G(τ) = (1 + B(τ,0)·B(L,τ))^{-1}` と厳密に一致。
- 前進スイープ中、境界 τ 到達時点でスライス ≥ τ は未更新なので、スイープ
  開始時に作った suffix は常に有効。整合性 OK。
- `udv_inv_one_plus_work` の大小分割 (Db/Ds) と符号計算
  (det T = 1 を単位上三角性で保証、U は直交、M は well-conditioned) は正しい。
  T が単位上三角であることは lmul/rmul/combine の全経路で保たれている。
- 物理への影響: 丸め誤差の再配分のみ。QUEST/ALF と同じ標準手法。

### (2) 遅延 rank-k Green 更新 — 妥当(逐次 rank-1 と数学的に同値)

- `green_delay_accept` は受理判定の対角 (`green_delay_ratio_N`)、更新ベクトル
  u の列、v の行のすべてに pending 補正 `G̃ = G − C Vᵀ` を厳密に反映して
  いる。打ち切り・近似は入っておらず、「近似遅延更新」ではない。
- 添字も確認済み: `g[j+i*n] = G_ji`(列 i)、`g[i+k*n] = G_ik`(行 i)で
  u_j = δ_ij − G̃_ji, v_k = G̃_ik。flush は 1 回の dgemm。数学的に厳密。
- 「old と bit 一致」は理論保証ではない(演算順序が変わる)。受理判定の
  margin ≫ 1e-15 なら軌道一致は十分起こり得るので観測事実としては妥当だが、
  文書では「本検証ケースでは bit 一致」と限定表現にすべき。

### (3) 半充填 PH 対称性 — 妥当(厳密恒等式、ガードも適切)

- λ = acosh(e^{ΔτU/2})、HS 恒等式 (n↑n↓ 非対称形 + c = −ΔτU/2) を確認。
  μ = U/2 は `model_init` で K 対角に注入。整合。
- `G↓_ij = δ_ij − P_iP_j G↑_ji` (`green_build_ph_down`) と down 比率
  `R↓ = 1 + G̃↑_ii N↓` (`green_ph_down_ratio_N`、P_i² = 1 で対角は
  1 − G↓_ii = G↑_ii) は正しい。pending 補正込みの対角を使う点も整合。
- ガード: `ph_symmetric = half && is_bipartite`。`lattice_from_file` は
  BFS 2 彩色で実ホッピングから二部性を検証するので、model 層では t' を
  足すと `ph_symmetric=0` になる。ただし現 `main.c` は非二部格子を
  v1 scope 外として abort するため、「two-spin 経路へ自動フォールバック」
  ではない。APBC はボンド符号を変えるだけで二部性・PH 対称性を壊さない
  (P_iP_j = −1 の副格子間ボンドなら t の符号によらず成立)。OK。

### (4) 交互スイープ + スタック繰り越し — 構造は正しいが、ドリフトが最大のリスク

- アルゴリズム整合性を確認: 前進で保存する prefix P[j] = B(b_j,0) は、後退
  スイープがスライス < b_j を更新する前にのみ使われる。後退で保存する
  suffix B(L,b_j) は更新済みスライスのみを含み、次の前進で有効。境界の
  端数 (L % stab ≠ 0) も `b[j] = min(j·stab, L)` で正しく処理。
  逐次スイープの定常性はスイープ順序に依らないので、マルコフ連鎖としても
  正当。
- **リスク**: β=16/stab=8 で wrapped-G ドリフト max_inf = 1.47。ドリフト
  した G で受理判定するため、安定化は G を修復しても**受理済みの場配位の
  履歴は修復しない**。これはサンプリング分布の系統バイアスであり、統計
  誤差では消えない。opt-in に留めた判断は正しい。
- 補足: 旧 production 比 68–70× の比較に使った `alt_9f785f8_20260703`
  run は `sweep_order=alternating`, `stab=4` を含む。したがって総合 speedup
  は、(1)(2)(3)(5) の数学的厳密性だけでなく、交互スイープ `stab=4` の
  旧実装との統計的一致検証にも依存する、と明記して扱うべき。
- **原因の有力候補**: `udv_rmul` (linalg.c) は M = D·(T·B) を直接 QR して
  いる。行スケーリングされた行列の Householder QR は、lmul の
  (B·U)·D(列スケーリング)と違い小さいスケールの情報を失いやすい。
  後退スイープの left_u 蓄積と suffix スタック構築はすべて rmul、前進の
  prefix 蓄積は lmul — 後退のドリフトが 1 桁以上大きい観測と整合する。
  対策候補は dgeqp3(列ピボット QR)を第一候補とする。転置 QR
  (Bᵀ·Tᵀ·D の列スケール QR → 転置して戻す)も候補だが、UDT 形式へ戻す
  導出と `U` 直交性・`T` 単位上三角性・det sign の回帰テストを先に固定する
  必要がある。

### (5) レプリカ MPI — 統計的に健全

- sign folding は per-bin で Σ sign·O / Σ sign。正しい。
- シードは splitmix64 ミキシング + 全対衝突チェック。xoshiro256** の
  jump() は未使用だが、周期 2^256 に対し使用乱数 ~10^8/レプリカなので
  実用上問題なし(jump() 化は安価な保険)。
- 純 MPI × sequential MKL 最速の結論は n=64–256 の行列サイズでは当然の
  結果で妥当(スレッド化 BLAS の同期コスト > 並列利得)。

## 2. 計算結果を変えるおそれ(重要度順)

- **R1(高)交互スイープのドリフト 1.47**: 上記 (4)。本番解禁の条件として
  (a) stab ≤ 4 必須、(b) production 条件ごとに calibrated drift guard を
  置くこと、(c) rmul の安定化改修、を推奨。絶対閾値 `1e-6` は現実的でない:
  既存検証では alternating/stab=4 でも max_inf=0.187、forward/stab=8 でも
  0.083 が出ており、これらまで fail させてしまう。ガードは「参照 run
  からの悪化率」「stab=2 参照との観測量差」「急激な drift jump」の組合せで
  決める方がよい。現行の `stab_drift` 診断は
  安定化毎に `green_from_scratch` (O(n³L)) を回すため常時オンにできない —
  数十スイープに 1 回のサンプリング監視モードがあると production で使える。
- **R2(中)誤差棒の信頼性**: 測定は毎スイープ、ビン = nmeas/nbin
  スイープ。自己相関時間 τ_int がビン長に近いと誤差過小評価になり、
  z_D = 2.39 (APP β=8) の解釈が揺らぐ。ビンサイズ倍増スキャン(誤差が
  頭打ちになるまで)を一度実施しておくべき。なお比較 ~13 項目で
  max|z| = 2.4 自体は確率的に許容範囲。
- **R3(中)前進モードでも stab=8 のドリフト 0.083 は大きめ**:
  stab=2–4 常用の方針は正しい。stab スキャンで E, D の系統変化が誤差以下で
  あることの定量化(post-ph-stab-scan の拡張)を production パラメータで
  一度残しておくと安心。
- **R4(低)「bit 一致」表現**: (2) 参照。限定表現へ。
- **R5(低)総合 70.01× が β=2/4/8 で同一値**: 全 β 合算 walltime 比を
  各行に転記していると推測される。β 依存(β²→β)を主張する文書なので、
  per-β の値に直すか合算値であることを明記すべき。
- **R6(低)`udv_inv_one_plus` の T 逆行列を LU (`la_inverse`) で計算**:
  T は単位上三角なので dtrtri/dtrsm が速くかつ正確。現状も正しいが、
  低温での精度マージンをわずかに損している。

## 3. 更なる高速化案

### 近距離(実装コスト小)

1. **dtrtri/dtrsm 化**: `udv_inv_one_plus_work` の T⁻¹ (LU+dgetri) を
   三角ソルブに。スタック導入後のホットパス (`green_from_stack`) に直接
   効く。精度も改善(R6 と同根)。
2. **delay capacity のパラメータ化と拡大**: 現状 16 固定
   (green.c `GREEN_DELAY_CAPACITY`)。n=256 なら k=32–64 が最適の可能性。
   合わせて pending 補正の p ループ(stride-n アクセス)を dgemv 化。
3. **安定化点ごとの測定**: G が厳密になる各境界で等時間測定(τ 並進不変
   なので期待値は同一)。1 スイープあたり最大 M ≈ L/stab 倍のサンプル。
   相関はあるが誤差改善はほぼタダ。
4. **対称 Trotter** B = e^{−ΔτK/2} e^{V} e^{−ΔτK/2}: Δτ² 係数が減り、
   同精度で Δτ を大きく = L を減らせる。壁時計に直結。
5. Makefile の `-O2` → `-O3 -march=native`(gcc/clang 側)。

### 中距離(アルゴリズム)

6. **チェッカーボード分解**(または並進対称性の FFT 適用): e^{−ΔτK} の
   適用を O(n³) gemm → O(n²) スパース適用に。wrap・B ブロック構築・
   スタック構築の全てに効く。Trotter 誤差の構造が変わるため Δτ 外挿の
   再検証が必要。
7. **サブマトリックス更新** (Nukala et al. PRB 80, 195101; DCA++/QUEST):
   遅延更新の上位互換。大 n でのキャッシュ効率がさらに良い。
8. **udv_rmul の安定化改修**(転置 QR or dgeqp3): 高速化ではないが、
   交互スイープ 1.24× を本番で安全に回収するための鍵(R1)。
9. **自己相関の削減**: 低温 16×16 では τ_int が支配する可能性。
   (a) 時間方向グローバル更新(1 サイト全スライス同時フリップ)、
   (b) パラレルテンパリング(E(T) スキャンの β 梯子を流用)。
   壁時計あたり独立サンプル数で効く。

### 大規模並列・GPU

10. **レプリカ MPI の scale-out**: 現構造のまま数千 rank まで weak scaling
    が期待できる。追加すべきは (a) xoshiro jump() による保証付き独立
    ストリーム、(b) チェックポイント/リスタート(長時間 production 用)。
11. **GPU 化はレプリカ・バッチングが本命**: n=256 の行列 1 個では GPU を
    飽和させないため、1 GPU に数百レプリカを載せ、cuBLAS batched dgemm
    (wrap/B ブロック/delay flush/combine)+ batched QR (geqrfBatched) で
    ホットパスを全てバッチ化する。受理判定の逐次ループは
    1 レプリカ = 1 スレッドブロックで対角 + pending 補正(O(n·k) の内積)
    のみ計算。メモリ試算: β=16, stab=4, n=256 で G+スタック ≈ 90 MB/
    レプリカ(交互モードは約 2 倍)→ 80 GB GPU で数百レプリカが載り、
    ちょうど統計要求と釣り合う。期待値: 1 GPU ≈ 数百 CPU コア相当。
    参考実装: DCA++ (Summit)、QUEST-GPU、SmoQyDQMC.jl。
12. **大格子 (24×24〜32×32, n ≥ 576) への道**: n³ gemm が単体で GPU 効率
    良くなるため、1 レプリカ = 1 GPU の単純オフロード(cuSOLVER QR)で
    十分。分散 QR/ScaLAPACK は n が数千を超えるまで不要。
13. **混合精度**(FP32 更新 + FP64 安定化)は研究的選択肢。安定化理論に
    直結するため、導入するならドリフト監視とセットで。

### メモリの注意

stab=2 常用 + 交互モード + ノード内多 rank の組合せはスタックメモリが
効く: UDV スタックは (M+1)·(2n²+n)·8 B/スピン。メモリ見積もりは
`dtau` と PH/two-spin 経路で変わるため、必ず条件を併記する。例えば
16×16, β=16, `dtau=0.1`, stab=2 なら M=80 で 1 スタック約 85 MB/スピン。
PH 経路の forward は主に 1 stack、交互モードは up 用 2 stack で約 170 MB/
レプリカ。two-spin で同じ構成を持てばさらに約 2 倍。120 rank/ノードなら
20–40 GB/ノード級になり得るので、ノードメモリと要相談。

## 結論

- (1)(2)(3)(5) は**数学的に厳密な再編成であり物理を変えない**。実装も
  主張どおりであることをコードレベルで確認した。
- (4) 交互スイープのみ、ドリフト 1.47 という実測がある限り production
  投入は現状の opt-in 判断が正しい。rmul の QR 安定性が原因候補であり、
  dgeqp3 または導出済み転置 QR による改修 + calibrated drift guard で
  1.24× を安全に回収できる余地がある。
- なお 68–70× の旧 production 比は `sweep_order=alternating`, `stab=4` を
  含む実測であり、「厳密な再編成だけの速度比」とは分けて読むべき。現時点の
  妥当性根拠は、旧実装との E/D の z-score 検証と sign=1/dN=0 の半充填
  sanity である。
- 統計面では、ビンサイズスキャンによる誤差棒の検証が z 値ベースの
  「物理量一致」主張を締めるために必要。
- 次の一手として費用対効果が高いのは: dtrtri/dtrsm 化、delay k の
  パラメータ化、安定化点測定、対称 Trotter。中期はチェッカーボード、
  長期はレプリカ・バッチング GPU 化。
